# Ulbo 博客本地 CMS：分阶段制作与验收计划

> 状态：实施中（阶段 0–2 已完成，阶段 3 开始）。
> 目标仓库：`Miles-gift/miles-gift.github.io`；正式发布分支：`main`。  
> 目标体验：在本机运行一个与现有 Ulbo 网站风格一致的简洁管理界面，完成文章和博客页面文案的新增、修改、删除、预览，并通过一个“检查并发布”按钮把准备好的内容提交、推送到 GitHub，随后查看部署结果。

## 一、目标、边界与完成定义

### 1.1 必须完成的用户能力

1. 在本机运行 `npm run cms` 后自动或按提示打开本地管理界面；停止命令后管理服务结束。浏览器直接访问公开站点时看不到 CMS。
2. 从文章列表搜索、筛选、打开、创建、复制、编辑及删除文章；列表清楚显示标题、slug、发布时间、分类、标签和本地/线上状态。
3. 编辑文章的标题、发布日期、更新时间、摘要、正文、分类、标签、草稿状态、封面/文章 Hero 图片，以及正文图片。Markdown/MDX 原文始终可读、可继续手工编辑。
4. 编辑博客列表页的 Hero 标题、副标题、背景图片、归档标题、介绍语、空状态文案，以及默认文章 Hero 图片；需要显示在博客页的站点名称和摘要也提供入口。计数、分页、阅读时间等由代码计算的内容继续自动生成。
5. 在保存到本地、准备发布、已推送 GitHub、线上生效之间显示不同状态。用户能在发布前看到文件变化、预览页面、发现校验错误。
6. 一个“检查并发布”按钮依次完成校验、构建、只提交 CMS 管理的文件、推送 `origin/main`，并展示 GitHub Actions/站点状态。遇到冲突或失败时保留本地内容，不强推、不隐瞒失败。
7. CMS 自身使用站点的 Outfit / Plus Jakarta Sans 字体、颜色变量、明暗主题、卡片和按钮视觉语言；桌面与窄屏均可用。界面以“文章、编辑、博客设置、发布”四个主要入口为限，辅助字段折叠呈现。

### 1.2 发布语义

- **保存**：保存到本机的 CMS 工作区，不推送 GitHub，不改变线上站点。
- **本地预览**：用待发布内容生成临时预览，并打开文章或博客页；预览不等于已发布。
- **发布**：明确选择的内容通过检查后提交并推送到 `main`。GitHub Actions 继续负责构建和发布 GitHub Pages。
- **线上生效**：以 GitHub Actions 部署成功和生产站点抽查为准。Git push 成功不能直接标记为“网站已更新”。
- **草稿隐私**：私有草稿保存在被 Git 忽略的 `.local-cms/` 内。现有 `draft: true` 只表示 Astro 生产构建不展示；如果把这样的源文件推送到公开仓库，仍可从 GitHub 看到，因此 CMS 默认不把私有草稿放进公开仓库。

### 1.3 范围边界

- 本地 CMS 是开发工具；不在 `dist/` 中生成公开 `/admin` 页面，不引入公开写入接口，也不要求云数据库。
- 博客内容继续以仓库里的 Markdown/MDX 为最终来源；现有 Ulbo 页面布局、字体、动画和阅读交互继续由原模板负责。新增可编辑数据通过配置读取，不重做博客页面。
- 功能性 UI 文案（如导航按钮、下载 PDF 按钮）属于模板界面；本计划把文章内容、博客展示文案与图片纳入 CMS，不把每个界面按钮都变成编辑字段。
- 此阶段不建设多用户协作、审批、云端登录、评论管理和统计后台。

## 二、现状基线与需要处理的耦合

| 现有位置 | 当前事实 | CMS 对策 |
| --- | --- | --- |
| `src/content/blog/*.{md,mdx}` | 4 篇文章；文件名决定 `post.id` 和 `/blog/<slug>/` 地址。 | 继续以文件为发布数据；新建时显式选择 slug，已发布文章默认锁定 slug，改标题不改 URL。 |
| `src/content.config.ts` 与 `src/lib/content/frontmatter-schema.ts` | `glob()` 加载 Markdown/MDX，严格校验 `title`、`date`、`updated`、`description`、`draft`、`categories`、`tags`；正式文章须恰好 1 个分类和至少 1 个标签。 | CMS 表单共用同一校验契约，避免编辑器允许、构建却拒绝。 |
| `scripts/normalize-frontmatter.mjs` | 会按固定顺序序列化字段，并规范日期和英文标签。 | 保存格式与其一致；若增加 `cover` 等字段，同时更新脚本，保证 `frontmatter:check` 不删字段。 |
| `src/config/hero.ts`、`src/config/site.ts` | 博客 Hero、默认文章背景、站点名称和说明目前写在 TypeScript 中。 | 把需要编辑的内容值提到可校验数据文件；配置模块仍向原页面提供相同类型的数据。 |
| `src/pages/blog/[...page].astro` | 归档标题、介绍语、空状态文案写在页面里，分页每页 15 篇。 | 把展示文案接到 CMS 设置；保留分页算法及自动计数。 |
| `src/layouts/BlogPost.astro` | 所有文章共用默认 Hero 背景；正文、发布日期、更新时间、PDF、目录由模板渲染。 | 可选文章封面覆盖默认背景，回退逻辑保留；不改原有排版结构。 |
| `src/pages/articles/[slug].astro` | 旧 `/articles/<slug>/` 跳转页随当前文章自动生成。 | 删除/更名时明确处理旧地址，避免跳到不存在的文章。 |
| `.github/workflows/deploy.yml` | `main` push 触发 Astro 检查、测试、构建、部署；线上验证目前硬编码检查最初 4 篇文章和 4 个旧地址。 | 改成基于本次内容清单/构建产物的动态校验，确保新增或删除文章后不会误判。 |

当前只有 4 篇文章，且正文图片使用 `/illustrations/...`。CMS 新上传的图片统一进入专用目录，例如 `public/uploads/blog/`；已存在的插图继续可用。

## 三、建议架构与文件职责

### 3.1 运行方式

1. 增加 `npm run cms`，启动仅绑定 `127.0.0.1` 的 Node 本地服务；终端显示访问地址，并提示 Git/Node 前置条件。
2. CMS 前端与本地文件/Git 操作均由本机服务提供。浏览器只发送编辑指令；文件写入、校验和 Git 命令只能在本机服务端执行。
3. 服务端使用项目自身的 Node 环境，必要时加入仅供开发使用的 TypeScript 执行依赖；不在生产部署里运行该服务。
4. 预览复用现有 Astro 构建和路由：以临时快照覆盖待发布内容，启动或生成隔离的本地预览。预览结果能看到真实 Ulbo 页面，而不仅是一个近似的富文本视图。
5. 单实例运行：同一仓库重复启动时给出已有地址或清楚报错，避免两个进程同时写同一篇文章。

### 3.2 拟新增/修改的文件

| 路径（拟定） | 职责 |
| --- | --- |
| `tools/local-cms/server.*` | 本地 HTTP 服务、请求来源检查、静态 CMS 资源、生命周期。 |
| `tools/local-cms/content.*` | Markdown/MDX 与 YAML frontmatter 读写、文件 ID 和路径校验、原文保留。 |
| `tools/local-cms/workspace.*` | `.local-cms/` 中的草稿、待删除标记、备份、冲突检测。 |
| `tools/local-cms/publish.*` | 预检、构建、精确暂存、提交、推送、状态回传。 |
| `tools/local-cms/media.*` | 图片上传、格式与尺寸检查、Sharp 优化、引用统计。 |
| `tools/local-cms/ui/*` | 本地文章列表、编辑器、博客设置和发布状态界面。 |
| `src/data/blog-settings.json` | 可编辑的博客 Hero、归档文案和默认 Hero 资源路径。 |
| `src/config/hero.ts`、`src/config/site.ts` | 读取 CMS 可编辑值并传给现有页面；保留非博客功能的默认配置。 |
| `src/lib/content/frontmatter-schema.ts`、`scripts/normalize-frontmatter.mjs` | 增加可选图片字段，并共用或对齐编辑与构建校验。 |
| `.gitignore` | 忽略 `.local-cms/`、本地预览及备份。 |
| `doc/LOCAL_BLOG_CMS_USER_GUIDE.md` | 安装、日常编辑、发布、失败恢复和手工 Git 共存说明。 |

实现时以实际目录名称为准，但必须保持“CMS 本地工作区”和“公开仓库源文件”分开。新增依赖只为具体功能服务，并锁定在 `package-lock.json`。

### 3.3 数据模型与字段规则

| 字段/内容 | CMS 控件与规则 | 输出或影响 |
| --- | --- | --- |
| 文章标题 `title` | 必填单行输入；支持中文和标点，禁止空白标题。 | 文章 Hero、列表、搜索、RSS、SEO 标题。 |
| slug / 文件名 | 新建时从标题建议一个可读 slug，可手改并检测冲突；已有公开文章默认不可随意修改。 | `/blog/<slug>/`、旧地址跳转、站内链接。 |
| 发布时间 `date` | 日期时间控件显示 `Asia/Shanghai`；保存完整 `+08:00` 时间，不无提示重置。 | 排序、页面时间、RSS 和结构化数据。 |
| 更新时间 `updated` | 可留空；修改正文时提示设置，不擅自改动原值；检查其值是否是有效时间。 | 文章“最近更新”与 `dateModified`。 |
| 摘要 `description` | 可选多行输入；提供字数提示与自动摘录预览。 | 列表摘要回退、SEO、RSS。 |
| 分类 `categories` | 发布文章恰好 1 项；草稿可为空；保留源码数组格式。 | 文章元信息、筛选及结构化数据。 |
| 标签 `tags` | 标签输入框支持增删与已有标签建议；至少 1 项，去重，并与现有英文大小写/空格规范一致。 | 标签页、首页计数、搜索、文章元信息。 |
| 正文 | 默认 Markdown/MDX 源码编辑，支持常用插入动作、查找、未保存提示与实时字数；不重写用户手写语法。 | 文章正文、自动目录、搜索索引、PDF 内容。 |
| 文章图片 `cover`（拟增） | 可选；上传后预览；留空则使用全站默认文章 Hero。 | 文章 Hero、预加载图和对应 SEO 图片。 |
| 正文图片 | 拖入/选择图片后插入 Markdown 路径与可编辑 alt 文本。 | 文章正文；保留模板灯箱行为。 |
| 草稿 | 清楚区分“仅本地私有草稿”和“准备发布”；不把私有草稿自动加入 Git。 | 本地状态与发布队列。 |
| 博客页设置 | Hero 标题/副标题/背景图、归档标题/介绍、空状态、默认文章 Hero，以及博客相关站点名称/说明。动态文案仅允许受控 `{total}`、`{current}`、`{last}` 占位符。 | `/blog/` 及共享元数据。 |

MDX 文章保持原格式，不强制转为 Markdown；不认识的 MDX 组件或自定义语法应保留原文。表单只修改 frontmatter 时，正文按字节保留；修改正文时给出差异预览。

### 3.4 媒体与路径规则

- 仅接收确定允许的 PNG、JPEG、WebP；检查文件内容类型、文件大小和像素上限。已有 SVG 插图可继续引用，但新上传 SVG 暂不开放，以免把脚本内容当图片带入网页。
- 用 Sharp 生成合适尺寸和格式，去掉不必要的图片元数据；文件名稳定且不会覆盖已有资源。编辑器插入站点绝对路径，如 `/uploads/blog/<name>.webp`。
- 删文章时默认不连带删图片；提供“未被引用资源”清单，只有确认无其他文章引用后才删除图片。
- 服务端只允许访问固定的内容、设置、媒体目录；解析后的真实路径必须仍在允许目录内，拒绝 `..`、绝对磁盘路径和符号链接逃逸。

## 四、界面设计原则

- 使用现有 `src/styles/global.css` 的色彩、字体和明暗主题变量，在 CMS 自己的 CSS 中定义局部布局。正文预览使用原站 `.prose` 样式。保持一致的按钮圆角、边框、阴影、焦点态与缓动节奏。
- 桌面布局：左侧窄导航/文章清单，右侧编辑区域；小屏切成单栏。顶部固定保存状态和“预览 / 检查并发布”操作。
- “文章”页默认显示搜索框、状态筛选和简洁列表。每行只展示标题、日期、标签摘要、状态和操作菜单；删除放在菜单里并二次确认。
- “编辑”页首屏只显示标题、发布时间、正文及主要动作；分类、标签、摘要、更新时间、封面等归入可展开的“文章信息”。必要字段的错误贴近输入框展示。
- “博客设置”页只呈现真正会改变博客页面的文案/图片；动态计数显示只读预览。
- “发布”页呈现待发布文章、设置、图片、删除项和文件差异；发布中逐步显示校验、Git push、GitHub Actions、站点验证结果，并给出可点击的工作流链接。
- 尊重键盘操作、可见焦点、字段标签、错误朗读和 `prefers-reduced-motion`；在 390px、768px、桌面宽度验收。

## 五、分阶段实施

以下阶段在实施分支逐阶段提交、推送到 GitHub；最终验收后合并 `main`。开发期间的 CMS 发布操作先在测试分支演练，避免试验文章误上正式站点。

### 阶段 0：冻结基线、梳理范围与风险

**工作**

1. 记录当前 `main` 提交、远程地址、4 篇文章路径、图像引用、构建产物与现有 GitHub Pages 设置；检查仓库是否有未提交文件。
2. 为旧内容生成清单与哈希，保存可回退 Git tag。确认本机 Node 满足仓库 `>=22.12.0`、npm 满足 `>=9.6.5`，当前 Git 凭据可以向目标仓库推送。
3. 核对 GitHub Pages 发布来源是否选择 **GitHub Actions**；仓库曾出现额外默认 Jekyll 检查失败，实施前应辨明配置并避免 CMS 把“某个检查失败”误报为站点发布失败。
4. 列出博客页和文章页全部用户可编辑文案，确认哪些值应迁入 `blog-settings.json`，哪些是自动计算或功能性 UI。

**交付与验收**：基线记录、内容清单、回退点和字段清单；原站内容与样式无变化。阶段结束推送实施分支。

### 阶段 1：本地服务与安全边界

**工作**

1. 新增 `npm run cms` 和本地服务。只监听 `127.0.0.1` 的随机或固定可用端口；启动时确认项目根目录、分支和内容目录。
2. 实现最小 API：健康状态、文章列表、读取文章、保存工作区、读取设置。所有写入请求检查 `Origin`/Host 与一次性会话令牌；拒绝外部网页跨站调用。接口不回传本机任意文件内容。
3. 增加 `.local-cms/` 忽略规则、单实例锁和异常退出后的工作区恢复提示；禁止静态托管构建包含 CMS 文件和 API。
4. 建立 UI 外壳与主题切换，先展示真实文章列表和只读详情。

**交付与验收**：单命令能打开本地界面；外部地址无法访问；生产 `dist/` 没有 CMS 入口；窄屏/深色基础样式可用。推送阶段提交。

### 阶段 2：文章数据层与完整增删改

**工作**

1. 实现 Markdown/MDX frontmatter 解析、字段表单、原文编辑、保存和读取；共享现有 schema 约束，并与 `frontmatter:check` 的序列化结果一致。
2. 私有草稿/修改先保存到 `.local-cms/`；对已发布文章保留原始版本、修改版本及基础 Git SHA，以便后续冲突检查。新文章选择 slug，禁止重复与不安全路径。
3. 添加文章、编辑文章、复制为新稿、删除文章和从本地回收区恢复。删除操作先软删除到本地工作区；发布后通过 Git 历史仍可恢复。
4. 加入标签建议、分类选择、日期时区处理、字段校验、未保存离开提醒、Markdown 快捷插入和正文差异视图。
5. 上传正文图片与封面图；新增可选封面字段，更新 schema、frontmatter 规范化脚本和文章 Hero/SEO 回退。

**交付与验收**：四篇原文读写不丢字、不改变未编辑字段；新建、编辑、删除、撤销均可用；非法日期、空标题、重复 tag、slug 冲突和越界路径被拒绝；媒体引用可构建。推送阶段提交。

### 阶段 3：博客页面设置与准确预览

**工作**

1. 把博客 Hero、归档标题/介绍、空状态、默认文章 Hero 等编辑项迁到 `src/data/blog-settings.json`；把站点名称/博客说明的编辑入口接到现有站点配置，避免使用字符串替换直接改 TypeScript。
2. 在 `src/pages/blog/[...page].astro` 和 `src/layouts/BlogPost.astro` 读取这些值，保持原 Ulbo 结构、字体、交互和响应式布局。动态总数、当前页、末页由现有计算结果填入允许的占位符。
3. CMS 中提供即时 Markdown 预览和“在网站中预览”。后者用临时隔离快照叠加待发布内容运行 Astro；验证生成的文章、目录、代码块、数学公式、Mermaid、图片与真实页面一致。临时产物退出后清理，不提交 Git。
4. 标明 MDX 自定义组件的即时预览能力边界；当即时预览不足时以 Astro 页面预览及生产构建为准。

**交付与验收**：博客设置每一项都反映到对应页面；文章预览与最终构建一致；站点原有搜索、标签、RSS、主题切换不回归；各屏宽视觉检查通过。推送阶段提交。

### 阶段 4：一键发布与 Git/GitHub 状态

**发布流水线**

1. 在“检查并发布”按钮开始时冻结本次待发布清单，展示新增、修改、删除、图片和博客设置；私有草稿默认不进入清单。
2. 检查当前仓库、`origin`、目标 `main`、Git 身份和认证、未完成 merge/rebase、未推送的其他本地提交。运行 `git fetch origin main`；若远端有新提交，对涉及文章做冲突检查，不能安全快进时停止并提示处理，绝不覆盖远端。
3. 备份将要修改的源文件；把确认发布的 CMS 工作区内容以临时文件写入并原子替换到允许的源目录。执行 `npm run frontmatter:check`、`npm run check`、`npm test`、`npm run build`，任一步失败即停止推送并保留可恢复的草稿和备份。
4. 仅对本次 CMS 管理的内容/设置/上传资源执行精确路径暂存；检查暂存差异与文件白名单，确保不会把 `.env`、其他代码改动或未选草稿一起提交。无变化时不产生空提交。
5. 生成清楚的内容提交信息，推送 `origin/main`。被拒绝的非快进推送不自动 rebase/force push；保留本地提交并提供“拉取远端后重试”的说明。
6. 推送成功后查询本次 SHA 对应的 Astro Pages 工作流状态（允许 API 限流/离线时回退到工作流链接），并访问实际站点检查这次新增/修改文章及博客首页。状态分别显示“已推送”“构建中”“部署成功”“线上检查失败”。
7. 确认部署成功后归档本地工作区版本；若部署失败，展示失败阶段和工作流链接，保留草稿与提交，提供修复后重新发布入口。

**配套调整**：把 `.github/workflows/deploy.yml` 中目前固定的四篇文章与旧地址检查改成读取本次实际存在的文章列表/构建清单；删除文章后不再检查已经删除的路径。发布删除时明确说明旧 URL 将失效，必要时提供预先确认的跳转目标。

**交付与验收**：在测试分支模拟正常发布、认证失败、无网络、远端先有新提交、构建失败、误混入其他未提交文件、删除旧文章等情况；每种失败都不丢内容、不强推。正式站点首次演练只发布一项可核对的测试变更。推送阶段提交。

### 阶段 5：体验收敛、文档、正式验收

**工作**

1. 从“新建文章 → 保存本地 → 预览 → 设发布时间/分类/tag → 检查并发布 → 查看线上”完整走通；再分别演练修改、删除和恢复。
2. 对照现有 Ulbo 站点检查 CMS 字体、明暗主题、卡片、按钮、动效和布局；检查键盘、屏幕阅读器标签、长文编辑、窄屏、断网提示。
3. 验证新增/修改/删除后首页最近文章、`/blog/`、文章页、标签页、搜索索引、RSS、sitemap 和旧地址处理一致；不让草稿进入公开页面或 GitHub 仓库。
4. 编写短操作手册、故障恢复说明和“CMS 与手工编辑 Markdown 如何共存”的规则；记录备份/回退命令。
5. 所有检查通过后合并实施分支到 `main` 并推送，观察 GitHub Actions 与线上结果。删除测试内容，确认仓库干净。

**交付与验收**：可使用的本地 CMS、操作手册、功能/视觉/安全验收记录；正式站点上线后能够用 CMS 独立完成一次内容更新。

## 六、关键测试清单

| 测试场景 | 预期 |
| --- | --- |
| 编辑 4 篇现有文章之一的标题/时间/正文/tag | 本地预览正确；保存不会改变未编辑正文；发布后列表、文章、标签、搜索、RSS 均同步。 |
| 新建中文长文并上传图片 | slug 唯一，图片路径有效，构建后图片可访问，Markdown 原文可读。 |
| 修改文章标题但不改 slug | 原文章 URL 稳定，旧链接仍可访问。 |
| 删除文章 | CMS 先显示回收状态；发布确认后文章、标签计数、搜索、RSS、sitemap 均移除；旧地址结果符合事先提示。 |
| 私有草稿 | 仅存在于 `.local-cms/`；`git status`、GitHub 源码和线上站点都看不到。 |
| 时间与标签异常 | 无效时间、重复标签、缺少正式文章分类/tag 被表单拦截，错误信息具体。 |
| 远端已更新/本地有其他改动 | 发布停止且保留稿件；不会将其他文件或旧版本推上 `main`。 |
| Git push 失败或 Actions 构建失败 | 界面显示准确阶段和可重试方式；不宣称线上已经更新。 |
| API 被外部网页调用 | 非本机来源、无令牌或非法路径请求被拒绝。 |
| `npm run build` | `dist/` 只含公开站点内容，不出现 CMS 管理页和本地草稿。 |

## 七、阶段提交、回退和待确认决策

- 每阶段记录完成内容、命令结果、已知问题及 commit SHA，推送实施分支。正式 CMS 发布功能在合并前只指向测试分支演练。
- 原文章和配置可通过阶段前 tag、Git 历史和 `.local-cms/` 备份恢复。发布功能不使用 `git push --force`、`git reset --hard` 清理用户工作区或宽范围 `git add .`。
- 计划默认：CMS 只供这台电脑上的仓库使用；单作者；正式发布目标为 `origin/main`；文章 URL 以 slug 为准并保持稳定；“一键更新”包含内容校验、Git commit/push 和部署状态反馈。
- 实施中若需要修改这些决定（例如支持多人同时编辑、从手机远程管理、改用云端后台），应先更新此计划并明确新增的数据同步和权限设计。
