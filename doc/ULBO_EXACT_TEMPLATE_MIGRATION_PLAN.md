> 本文取代 `doc/ULBO_FULL_MIGRATION_PLAN.md` 中“保留原站四类内容、CMS 和既有前端并套用 Ulbo 风格”的实施路线。

## 0. 目标的准确含义

把 [Astro 主题页上的 Ulbo](https://astro.build/themes/details/ulbo/) 对应的[官方模板仓库](https://github.com/xxy1103/ulbo-astro-theme-template)作为**新网站的源工程**。首页、文章归档、标签、关于、文章详情及其导航、字体、图片、颜色、排版、响应式布局、暗色主题、动画、页面过渡和交互均遵循模板原实现。本站只注入作者真实的个人资料与长篇文章，并为 `miles-gift.github.io` 做必要的部署配置。

这意味着从上游模板开始，而不是继续改造目前的 Momo 站点，也不是凭截图重新创作一个“Ulbo 风格”站点。任何与上游不同的前端代码都必须能归入下列三类：**作者内容填充、真实身份及站点元数据配置、GitHub Pages 部署兼容**。实施时建立差异清单；清单外的样式、布局和交互改动一律撤回。

“其余部分一概不要”在本方案中的具体范围：原站的资料库、短想法、旅程、专题页、现有 CMS、Pagefind、Momo 组件、先前原创 Hero、原站设计令牌和自定义排版，均不进入新的公开站点。Ulbo 模板本身的博客、标签、搜索、归档、关于、RSS 等组成部分则按原版保留；它们服务于迁入的四篇文章，不作为原站栏目继续运营。上游演示文章、虚构头像及占位姓名/联系方式也不能出现在成品中。

## 2. 整体实施规则与变更边界

1. 在 `codex/ulbo-exact-template` 专用分支实施；每阶段完成后提交并推送该分支。直到全部验收通过，`main` 和线上站点不切换。这样满足逐阶段留档，同时避免把半成品依次发布到 GitHub Pages。
2. 建立“上游原版 → 本站”的差异表。每一项差异标注：配置、内容、部署、许可/安全修正，附文件、原因、复核人/记录。视觉 CSS、组件 DOM、动效脚本应保持零自主改造；若必须修复模板在目标环境中的实际故障，记录可复现故障与最小补丁。
3. 不升级 Astro 主版本、不把 npm 换成 pnpm、不重写搜索引擎或动画库。上游模板使用 Astro 6、npm；部署只适配 GitHub Pages。只要上游版本正常通过构建，就沿用其锁文件和脚本。
4. 对文章进行**格式映射**，不做润色、删节、重新概括或改写观点。因为旧站的元信息不符合 Ulbo 严格 schema，只有 frontmatter 字段名和必要的资源路径可以改变；正文段落应有迁移前后差异/哈希检查。
5. 对未取得合法使用依据的第三方素材，暂停其上线并记录来源问题。模板代码的 MIT 许可须保留；字体与图片按各自授权核查。素材问题只能通过取得原素材授权或取得视觉上可对照、授权明确的替代品解决，不能在未记录的情况下私自改成另一种设计。
6. 每个阶段的完成标准都包含：变更可复核、对应检查通过、独立 commit、远端分支已更新。未达标不进入下一阶段；失败留在分支修复，不合并到 `main`。

## 3. 分阶段执行

### 阶段 0：冻结目标、备份现站和建立对照基线

**动作**

1. 记录 `main` 的提交 SHA、远端、GitHub Pages 当前部署方式、站点可访问 URL 和工作区状态；创建只用于回溯的旧站 tag/备份分支。
2. 从官方仓库取得完整 Ulbo 模板；记录准确 commit 与 `LICENSE`；运行上游原项目的 `npm ci`、`npm run check`、`npm test`、`npm run build`，保存结果。
3. 在相同浏览器、相同 viewport 和设备缩放下，给上游演示站首页、文章归档、标签、关于和文章详情分别截取桌面、平板、手机的浅/深色基准图。记录页面打开后、滚动后、悬停/聚焦、搜索弹窗、移动菜单及转场状态；视频录制动画时长/顺序以便复核。
4. 对 Ulbo 文件树做 manifest：源代码、静态资源、配置、演示文章、部署脚本与依赖。单独列出允许改的文件及原因。
5. 盘点四篇文章的完整 frontmatter、正文、图片链接及旧 URL；保存逐篇正文基线。确认公开个人资料的来源和明确不公开的字段。

**产物**：上游版本锁定记录、旧站回退引用、文章/资产/路由盘点、视觉/交互基准图、差异白名单。

**通过条件**：能从记录复现同一版模板；四篇文章及个人资料均可定位；旧站可由 Git 引用恢复；基准覆盖宽度至少 390、768、1440 px 与浅/深色。阶段提交、推送开发分支。

### 阶段 1：以 Ulbo 原项目替换原站工程

**动作**

1. 以冻结的上游模板文件树作为目标分支的新工作树；保留 `LICENSE` 与必要的上游说明。原站源码不是迁移底座。
2. 移除 Momo 的页面、组件、样式、旧内容集合、CMS 子项目、Pagefind 文件、旧工作流以及旧依赖和锁文件；保留旧内容的 Git 历史引用供后续迁移核对。
3. 保留模板自身完整的首页、博客、标签、关于、搜索、RSS、站点地图、robots、404/缺省行为与所有视觉资产。仅去除 `src/content/blog` 中的上游演示文章和任何会展示虚构个人资料的示例内容。
4. 不调整模板的 `global.css`、Hero、导航、字体、卡片、阅读布局或转场脚本。生成完整差异清单，特别检查是否无意带入原站 CSS、组件或脚本。
5. 用空内容集验证模板仍能构建，确认有内容后再进行下一阶段；如上游允许空博客，应按其默认行为呈现。

**产物**：可构建的原版 Ulbo 工程骨架、清除旧设计的文件差异与上游比对表。

**通过条件**：项目目录、路由、依赖和核心前端文件与上游一致；新工程没有旧站栏目/旧 CMS/旧搜索组件；`npm ci`、`npm run check`、`npm test`、`npm run build` 通过。阶段提交、推送开发分支。

**产物**：真实站点配置、原版关于页上的真实信息、占位信息扫描报告。

**通过条件**：页面和生成 HTML 无模板示例身份；关于信息与原公开资料一致；无虚构邮箱/头像/履历；模板布局和动效文件无非必要改动。阶段检查、提交、推送。

### 阶段 3：将四篇长文迁入 Ulbo 的 blog 集合

**动作**

1. 在 `src/content/blog/` 建立恰好四个条目，使用原 `slug`，以 Ulbo 原生 `/blog/<slug>/` 为 canonical 地址；全部为公开文章，不附带演示文章。
2. 严格按上游 schema 映射：旧 `title → title`、`pubDate → date`、`description → description`、`draft → draft`、`topic → categories` 的单元素数组、`tags → tags`。确有旧 `updated` 时才映射 `updated`；旧 `kind`、`series`、`cover`、`featured` 等模板不支持的字段不塞入新 frontmatter，也不为它们改 schema。保持日期及标签原值。
3. 逐篇复制 Markdown 正文。只修正站内路径和资产引用；《内容不是文件》所用的 `/illustrations/content-loop.svg` 和 `/illustrations/publication-boundary.svg` 随文章迁入，并核验它们不会被用于其它旧栏目。
4. 审核正文里的旧站导航、栏目名称、内部链接。如果属于作者文章原文叙述，原则上保持原文；如果它是已失效的功能链接，则仅改链接目标或去掉失效导航，逐项记录，不悄悄删段落。
5. 对比迁入前后：四篇标题、发布日期、简介、标签、正文段落/标题/代码块/图片的数量与内容；记录每篇差异。运行 Ulbo 的 frontmatter 校验。
6. 使首页、归档、标签、搜索索引、RSS 和 sitemap 均从这四篇文章自然生成；不手工补进资料、想法和旅程。

**产物**：四篇可渲染的 Ulbo 博客文章、两张必要插图、逐篇内容差异记录。

**通过条件**：blog 集合恰好四篇公开文章；四条 `/blog/<slug>/` 可构建；文章正文及图片无缺失；标签/搜索/RSS/sitemap 只收录目标内容；上游 frontmatter 校验、测试和构建均通过。阶段提交、推送。

### 阶段 4：旧地址处理与外部发布环境适配

**动作**

1. `/blog/<slug>/` 保持 Ulbo 原生文章地址。针对旧站四条 `/articles/<slug>/` 建立最轻量的静态跳转页或等效 GitHub Pages 兼容方案，目标分别指向对应 blog 页面；跳转页不进入导航、搜索、RSS 和 sitemap，并设置 canonical/noindex，避免重复索引。检查旧 `/blog/<slug>/` 的反向跳转逻辑已被移除，防止循环。
2. 旧 `/resources/`、`/thoughts/`、`/journey/` 及其详情不迁移为新站内容，也不在页面推荐、搜索索引或导航中出现。旧 URL 可能被外部引用；在验收记录列出这项有意的下线影响，而非暗中重建旧栏目。
3. 将上游 Cloudflare/Wrangler 发布流程适配为目标仓库既有的 GitHub Pages Actions：Node 符合上游要求，`npm ci`、`npm run check`、`npm test`、`npm run build`，上传 `dist` 并部署 Pages。只更改工作流、`astro.config.mjs` 的 `site` 等部署必需配置；不因此改动前端。
4. 检查绝对资源路径、页面末尾斜杠、字体加载、RSS、robots、sitemap、canonical、OG 地址在 `https://miles-gift.github.io/` 下均正确。移除旧站特有的路径、域名和 CI 检查脚本。
5. 核对 MIT 许可保留；逐个核验默认背景图、头像、字体及文章插图的使用权限。对于无法确认的背景素材，记录为上线阻断项并取得合法来源或经审查的同视觉替代资产。

**产物**：GitHub Pages 工作流、四篇旧文章的地址迁移、许可与素材来源记录。

**通过条件**：预览环境能打开四个新地址及四个旧文章跳转；没有跳转环；新站不生成已排除的栏目；本地构建及 Actions 检查通过；素材使用有依据。阶段提交、推送。

### 阶段 5：原版视觉、响应式与交互逐项验收

**动作**

1. 对照阶段 0 的**同版本 Ulbo 演示站**，逐页检查：首页 Hero 高度/裁切、导航透明与滚动状态、文字和图片位置、卡片宽度/圆角/阴影、文章列表密度、标签布局、关于页头像占位、详情页阅读宽度及目录。由于文案不同，比较组件框架与样式，而非字形像素完全重合。
2. 核对字体网络请求和 computed styles：Outfit、Plus Jakarta Sans、字号、字重、行高、字距、中文回退；浅/深主题分别检查。若字体请求失败，应先解决加载问题，不擅自换字体。
3. 录屏/逐帧核对首页打字效果、Hero 视差或滚动效果、悬停动画、主题切换过渡、页面 View Transition、搜索弹窗开闭、移动导航、目录定位、图片灯箱。核对时长、缓动曲线、动画方向和元素层级与上游一致。
4. 在 390、768、1440 px 宽度以及实际可用的浏览器中测试浅色、深色、系统减少动态效果；用键盘和触屏走通导航、搜索快捷键、分页、标签、目录、图片。检查没有横向溢出、遮挡、错误焦点或闪烁。
5. 对每个前端差异做审查：若不是作者内容或部署必要项，恢复上游实现。任何与模板不一致的截图差异都须有记录、原因和处理结果，不可用“风格相近”判定通过。

**产物**：页面与交互对照截图/录屏、computed style 核对记录、差异关闭表。

**通过条件**：模板功能完整；核心页面在各尺寸和主题下与同版本模板的结构、字体、动效一致；所有非内容/部署差异均已消除或有明确可复核的兼容性说明；无阻断交互问题。阶段提交、推送。

### 阶段 6：完整质量检查、发布和线上复核

**动作**

1. 在开发分支运行 `npm ci`、`npm run frontmatter:check`、`npm run check`、`npm test`、`npm run build`。检查生成目录：四篇文章、预期标签与关于页、RSS、sitemap、robots、搜索索引均存在；旧栏目和演示人物内容均不存在。
2. 对全站输出做链接、图片、字体、favicon、canonical 与 JSON-LD 检查；对四篇正文做内容差异终检；审查仓库与模板的最终差异清单。
3. 整理最终验收记录：冻结的 Ulbo commit、本站 commit、四篇文章清单、个人信息来源、视觉/交互结果、许可情况、构建/部署结果及已知限制。
4. 在全部通过后将开发分支合入 `main` 并推送；等待 GitHub Pages Actions 完成，再访问生产网址，实测首页、`/blog/`、四篇文章、`/tags/`、`/about/`、搜索、RSS 和旧文章跳转。
5. 如线上发现样式/字体/资源缺失，优先在开发分支修复并再次检查后合并；若上线造成严重故障，以阶段 0 的备份引用恢复上一个可用部署，并在验收记录中注明。

**产物**：正式发布的新站、线上复核记录、最终验收文档及可追溯的阶段提交。

**通过条件**：生产站点确实运行 Ulbo 模板，显示且仅显示作者四篇长文与真实个人信息；字体、动画、特效、布局、浅/深色均通过与上游的对照；GitHub Pages 部署成功且核心 URL 可访问。最终提交和推送完成。

## 5. 阶段提交、记录与回退约定

阶段提交建议使用明确的 `stage-0` 至 `stage-6` 前缀，每个阶段一份短验收记录，包含变更文件、与上游差异、验证命令和结果、commit SHA、远端分支链接。阶段推送只更新 `codex/ulbo-exact-template`；最终验收通过后才合入 `main`，触发线上部署。旧站保存在 Git 历史及阶段 0 备份引用中，日后需要恢复时有确定的 SHA，不依赖本地未提交文件。

执行期间若出现新要求，应先判断是否属于“个人内容/真实身份/部署兼容”；超出范围的新增栏目、视觉创作和功能改造不混进本次任务。验收以**原版模板的实际源码与演示效果**为准，而非以之前的迁移计划、现站页面或主观“看起来相似”作为标准。
