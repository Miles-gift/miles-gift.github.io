在整理这个个人网站之前，我已经有不少文件：PyTorch 笔记、uv 命令、Git 学习标题、macOS 快捷键清单、雅思课程记录，还有一些比赛与评奖材料。它们看起来像是一个知识库，但当我真正尝试把它们变成网站内容时，问题立刻暴露出来：有的文件缺少上下文，有的混合了外部教程，有的只有标题，有的包含不适合公开的身份信息。文件数量并不能说明知识是否可用。

我需要的不是一次“上传整个文件夹”，而是一套能长期运行的内容系统。它应该回答：一条材料为什么值得保留；哪些事实经过确认；什么可以公开；访客如何找到它；半年后如何知道其中的命令是否仍然有效。这个系统还要足够轻，不能为了整理而制造比写作更多的负担。

![从捕捉、验证、整理、发布到复盘的内容循环](/illustrations/content-loop.svg)

上图是本站采用的五步循环：捕捉、验证、整理、发布、复盘。它不是瀑布流程。复盘产生的新问题会重新进入捕捉阶段，旧内容也可以回到验证和整理阶段继续修订。

## 一、先区分素材、记录与作品

最容易犯的错误，是把本地已有文件都称为“文章”。实际上，三者的责任完全不同。

**素材**是尚未处理的输入。课程视频、截图、证书扫描件、浏览器收藏和聊天片段都属于这一层。它们可能重要，但往往带有版权、隐私、时效或事实不完整的问题。素材可以提醒我曾经遇到什么，却不应该自动获得公开资格。

**记录**是带上下文的个人信息。例如我为什么收藏 PyTorch 官方教程、测试过哪个版本、哪里失败、下一次准备做什么。记录已经有了自己的判断，但未必足以让陌生读者独立理解。

**作品**是面向读者完成过编辑的内容。它有明确问题、必要背景、可复现过程、结论和来源，也经过隐私与版权检查。文章、资料导读、短想法和经历条目都可以成为作品，只是表达密度不同。

这一区分带来的直接变化，是不再用“是否存在 Markdown 文件”判断任务是否完成。一个只有标题的 `Git.md` 是素材；一条说明学习目标、阅读顺序和恢复风险的 Git 资料卡，才是可以继续使用的记录；一篇经过真实仓库验证的 Git 工作流文章，才是完整作品。

## 二、内容类型不是文件夹装饰

早期模板只有一个通用博客集合。学习资料、短想法和人生经历如果全部塞进文章，会出现两个问题：字段被迫取最小公倍数，页面也无法表达差异。一本书需要作者、来源和阅读进度；一条短想法不需要三千字结构；教育经历的日期精度可能只有年份，不能伪造具体日期来满足文章 schema。

因此本站把公开内容拆成五类：

| 类型 | 回答的问题 | 关键字段 | 页面重点 |
|---|---|---|---|
| Article | 我怎样理解并解决一个问题 | 主题、标签、系列、许可 | 长文阅读与前后关联 |
| Resource | 这份资料为什么值得使用 | 来源、类型、状态、进度、复核日期 | 导读、收获与官方入口 |
| Thought | 此刻最值得留下的一条判断是什么 | 时间、主题、关联内容 | 简短、直接、可连接 |
| Journey | 哪个阶段或节点改变了路径 | 发生时间、类型、来源级别 | 时间线与事实边界 |
| Page | 站点长期遵守什么规则 | 更新时间、可见性 | 隐私、版权等固定说明 |

内容类型的价值不是“目录看起来整齐”，而是让错误更难发生。资料没有 `sourceUrl` 就不能通过构建；Journey 的时间允许 `YYYY`、`YYYY-MM` 或 `YYYY-MM-DD`，从源头阻止伪精确；文章发布后保持稳定 slug，避免搜索结果和旧链接频繁失效。

## 三、先写约束，再追求数量

如果任何字段都能自由输入，十几条内容之后就会出现 `AI`、`人工智能`、`Artificial Intelligence` 三套同义主题，`进行中`、`学习中`、`learning` 三套状态。每个词单看都合理，组合起来却无法稳定筛选。

本站把相对稳定的概念放进受控词表：主题、资源类型、资源状态、Journey 类型、可见性和许可。一次性活动名、书名和技术名放在标签中。规则可以简化为：内容类型说明“它是什么”，主题说明“它长期属于哪里”，标签说明“这次具体涉及什么”。

一篇文章的最小 frontmatter 如下：

```yaml
title: 内容不是文件
slug: content-operating-system
description: 一段可以脱离正文独立理解的摘要
pubDate: 2026-09-10
draft: true
visibility: draft
kind: article
topic: 知识管理
tags: [内容系统, Markdown, Git]
lang: zh-cn
license: CC-BY-NC-SA-4.0
```

`draft` 和 `visibility` 同时存在看似重复，却表达两个不同问题：内容是否还在编辑，以及内容是否应该出现在公开列表。当前首发流程只让 `draft: false` 且 `visibility: public` 的条目进入生产列表、RSS 和详情路由。以后如果需要通过链接分享但不参与公开发现，可以使用 `unlisted`，而不是临时改路由或依靠“别人应该猜不到 URL”。

## 四、事实核验与叙事权必须分开

个人经历最容易出现另一种错误：证明材料可以验证结果，却不能自动证明个人贡献。证书能够说明某项赛事、年份与奖项真实发生，但通常不能说明我在团队中设计了什么、承担了多少工作、遇到了哪些失败。如果直接从奖项推导个人故事，文字可能看起来完整，事实却并不可靠。

因此 Journey 增加 `sourceLevel`：`user-provided` 表示本人明确提供并允许公开，`verified-summary` 表示只使用材料能够核验的最小摘要。对后者，页面可以写赛事、年份、团队结果和明确出现的项目名称，不写未经补充的个人职责，不展示证书编号、二维码、队友和指导教师身份。

教育经历也采用相同原则。本站公开 2020—2023 年江苏省靖江高级中学、2023 年至今华中科技大学，因为这些信息由本人明确提供；专业、班级、培养层次和日程没有获得同样授权，所以保持空白。空白不是缺陷，它比自动补全更可信。

![私人素材必须经过事实、隐私与版权检查后才能成为公开作品](/illustrations/publication-boundary.svg)

这条边界不等于把风险交给一次人工检查。内容模型、附件预检、固定页面说明和 Git 历史共同保留了判断依据：素材仍可留在合适的私人位置，公开仓库只接收经过转换、能够长期负责的表达。

## 五、版权边界决定“怎样转换”

本地学习目录里可能同时存在自己的笔记、他人的教程截图、课程课件和题库。把文件复制到公开仓库既不等于原创整理，也可能破坏原内容的授权边界。本站采用的转换方式是：保留线索，回到官方来源，重新建立自己的解释，再记录真实使用结果。

以 PyTorch 为例，本地笔记可以提示我曾关注张量和 `torch.nn`，但公开资料页只链接 PyTorch 官方基础教程，写明准备怎样跑通数据、模型、损失、优化和保存加载的闭环。以后形成教程时，代码必须在注明的 Python、PyTorch 和硬件环境中重新执行，截图也由自己的实验生成。

这套原则可以概括为四句话：

1. 不上传付费课程、题库、书籍或论文全文。
2. 不把外部教程换一种说法后伪装成原创。
3. 资料卡优先链接原始或官方来源。
4. 自己的价值来自选择理由、实验、失败、比较和结论。

## 六、把发布变成可以验证的事务

发布不是“保存文件”一个动作，而是一组必须同时成立的状态变化：内容通过 schema，路径唯一，生产构建成功，搜索和 RSS 得到更新，Git 远端接收提交，GitHub Pages 部署成功，线上页面最终可访问。任何一步失败，都不应假装发布已经完成。

可以把一次发布抽象成下面的检查序列：

```text
创建草稿
  → 本地预览
  → 内容与隐私复核
  → validate:content
  → production build
  → commit / push
  → GitHub Actions
  → 线上路径与搜索检查
```

其中 `validate:content` 会检查 frontmatter、标识与路径一致性、重复 URL、受控主题和高风险附件。Astro 的 Zod schema 继续检查日期、URL、枚举、长度、范围、必填字段和未知字段。两层校验的目标不是让写作变得官僚，而是让错误尽量在本地、在提交之前暴露。

## 七、用一个简单模型判断内容价值

内容是否值得公开，不能只看篇幅。我目前使用一个非严格的思考模型：

$$
V = \frac{R \times T \times F}{C_m + C_r}
$$

其中，$R$ 是可复用性，$T$ 是可信度，$F$ 是可发现性；$C_m$ 是持续维护成本，$C_r$ 是隐私与版权风险。这个公式不用于计算精确分数，而是提醒我：一篇很长但无法验证、无法搜索、需要频繁修补的文章，长期价值可能低于一条短小但准确的资料卡。

提高价值不只有“写更多”一条路。补充版本信息可以提高可信度；建立主题和标签聚合可以提高可发现性；把易变命令与稳定原理分开可以降低维护成本；只公开必要事实可以降低风险。内容系统的设计，就是把这些改进变成默认行为。

## 八、搜索、归档和关联不是发布后的装饰

如果内容只能从首页最新列表进入，几个月后它就会被新内容淹没。可发现性必须在内容模型阶段就被考虑。本站目前提供五种入口：主栏目说明内容类型；主题聚合同一长期领域；标签连接具体技术与方法；归档保留时间顺序；Pagefind 在浏览器本地搜索正文。

关联也应该遵循明确规则。文章推荐优先比较主题与共享标签，短想法通过 `related` 指向它延伸或修正的文章、资料。系统不会为了增加点击随机推荐，也不会把不存在的关系写成“猜你喜欢”。当内容数量较少时，宁可显示两条真正相关的链接，也不填满一个看似热闹的推荐区。

## 九、每次复盘都要能改变系统

复盘如果只写“这次做得不错”，对下一次没有帮助。一次有效复盘至少回答四个问题：哪里耗时超出预期；哪个错误本可以提前发现；什么检查值得自动化；哪条规则已经不适合真实内容。

例如这次迁移让我确认：旧 CMS 虽然仍能构建，却还在写已经废弃的 `content/blog`。如果只测试“CMS 页面能打开”，就会得到错误的安全感。因此 README 明确标记阶段 6 前暂停用旧表单保存内容，并把“用 CMS 完整发布一篇真实内容”设为恢复可用的验收条件。

同样，公开 PageSpeed 服务可能因为额度不可用，所以性能验收不能只依赖一个远程 API。后续会保留本地 Lighthouse、构建产物检查和真实移动端测试三种证据。工具失败不是跳过验收的理由，而是提醒系统不能只有单点依赖。

## 十、一个可持续系统应当允许慢下来

个人知识库最危险的指标，是用条目数量代替理解深度。快速导入一百个文件很有成就感，却会留下来源不明、重复、过时和无法维护的内容债务。这个网站选择从少量真实内容开始：三类学习资料、一组短想法、明确的教育与成果节点，再逐步补充经过实践的长文。

“实时上传”也不等于未经检查立即公开。首发流程追求的是本地即时预览和推送后的分钟级自动发布，同时保留构建、版本和回滚能力。对于个人站，这种速度已经足够快，也比直接暴露写入后台更容易守住安全边界。

最终，我希望这套系统达到的状态很简单：想到一个问题时，可以快速捕捉；准备公开时，知道必须核验什么；发布以后，未来的自己仍然能够找到、理解和修正它。内容不再只是文件夹里的静态存量，而成为一条可以持续运行的学习循环。
